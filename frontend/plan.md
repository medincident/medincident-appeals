### 1.2 Что НЕ хватает в датасете — критические проблемы

#### A. Синтетичность и низкое разнообразие

**Проблема**: Все 3000 примеров сгенерированы из всего 120+15=135 шаблонов. Каждый шаблон
порождает ~23 вариации только за счёт 15 преамбул × 15 суффиксов. По сути, *ядро жалобы*
(complaint_core) в каждой вариации **абсолютно одинаковое**.

Пример: для шаблона "упал с кровати ночью, ударился головой, никто не пришёл когда позвал на
помощь" все 23 вариации будут:
```
"Здравствуйте! упал с кровати ночью, ударился головой... Прошу принять меры."
"Хочу пожаловаться. упал с кровати ночью, ударился головой... Это очень беспокоит."
...
```

**Почему это плохо**: Модель будет **запоминать фразы** (overfitting), а не учиться обобщать.
На реальных жалобах пациентов, которые пишут уникальными словами, модель будет работать хуже.

> **Термин: Overfitting (переобучение)** — модель запоминает обучающие примеры вместо того,
> чтобы выучить общие закономерности. Проявляется в высоком accuracy на train, но низком на
> unseen data.

#### B. Дисбаланс классов (Class Imbalance)

90% важных / 10% неважных — это **сильный дисбаланс**.

- Для **классификатора важности** (rubert-tiny2): модель может научиться всегда предсказывать
  "important" и получить accuracy 90% — но это бесполезная модель.
- Для неважного класса всего **15 шаблонов** × ~20 вариаций = очень бедное представление
  "не-жалоб".

> **Термин: Class Imbalance** — ситуация, когда один класс значительно преобладает. Метрики
> accuracy становятся обманчивыми. Нужны F1, Precision, Recall по каждому классу.

#### C. Дисбаланс подкатегорий

Разброс от 232 (sub_1_1 "Падения") до 64 (sub_5_3 "Обработка инструментов") — **разница в
3.6x**. Это значит:
- Модель category matcher будет лучше работать на частых подкатегориях.
- Редкие подкатегории (хирургические ошибки, обработка инструментов) будут классифицироваться
  хуже.

#### D. Отсутствие пограничных случаев (Edge Cases)

В датасете **нет** примеров:
- **Мультикатегорийных жалоб**: "Упал в палате, потому что пол мокрый, а ещё мне дали не тот
  укол" (cat_1 + cat_2).
- **Амбивалентных**: жалоба, которая может быть и cat_6 и cat_7 (условия + персонал).
- **Длинных текстов**: max=134 символа — реальные пациенты могут писать по 500+ символов.
- **Очень коротких**: "Упал." — 5 символов.
- **С нецензурной лексикой** (реальные жалобы).
- **Со смешанным языком** (транслит, украинский, и т.д.).
- **Ложных срабатываний**: "Мне сделали очень больно уколом, но врач предупреждал" — это не
  инцидент, но содержит ключевые слова.

#### E. Один и тот же формализованный ответ для всех вариаций

Все 23 вариации одного шаблона имеют **идентичный** formalized_text и theses. Модель seq2seq
учится, что разные входы с одним ядром должны давать один и тот же выход — это **не учит
перефразировать**, а учит запоминать.

#### F. Нет шума реальных данных

Реальные пациенты:
- Делают грамматические ошибки (не только 10 предзаданных замен).
- Пишут с телефона с autocorrect.
- Используют разговорный стиль, диалектизмы, сленг.
- Пишут со множественными жалобами в одном сообщении.
- Указывают имена врачей, номера палат, даты.

### 1.3 Необходимые манипуляции с датасетом перед тренировкой

#### Шаг 1: Аугментация данных (Data Augmentation)

> **Термин: Data Augmentation** — техники увеличения и разнообразения датасета без сбора новых
> реальных данных.

1. **Back-translation (обратный перевод)**: RU → EN → RU через Helsinki-NLP/opus-mt для создания
   парафраз. Каждый шаблон даст 2-3 уникальных перефразировки ядра.

2. **Synonym replacement**: замена слов на синонимы с помощью ruwordnet или word2vec — "упал" →
   "свалился", "грохнулся"; "холодная еда" → "остывшая пища".

3. **Random insertion/deletion**: случайное добавление/удаление слов для имитации реальной речи.

4. **Noise injection** — расширить набор опечаток с 10 до 50+ реальных паттернов клавиатурных
   ошибок, включая:
   - Пропущенные пробелы: "упалскровати"
   - Случайные символы: "упал с кроватт"
   - Автокоррект-артефакты

#### Шаг 2: Балансировка классов

> **Термин: Oversampling / Undersampling** — техники выравнивания представленности классов.

1. **Для бинарной классификации**: увеличить неважные до ~30-40% (сейчас 10%):
   - Добавить шаблоны: вопросы о расписании, приветствия, отзывы, запросы о wifi, TV, стоимости.
   - Целевой баланс: 70/30 или 60/40.

2. **Для подкатегорий**: выровнять до ~100-130 примеров на каждую через дополнительные шаблоны
   для редких подкатегорий (cat_3, cat_4, cat_5).

#### Шаг 3: Добавить пограничные случаи

- 50-100 мультикатегорийных жалоб (для оценки — как ground truth выбирать основную категорию).
- 30-50 "ложных тревог" — текст с медицинскими словами, но не инцидент.
- 50 длинных текстов (200-500 символов).
- 30 очень коротких (5-20 символов).

#### Шаг 4: Стратифицированное разделение (Stratified Split)

> **Термин: Stratified Split** — разделение датасета на train/val/test с сохранением пропорций
> каждого класса в каждой части.

**Текущая проблема**: `train_classifier.py` делает random split (0.85/0.15), а test set вообще
отсутствует.

**Правильная схема:**
```
dataset.jsonl (3000)
    ├── train.jsonl  (70%) — 2100 примеров
    ├── val.jsonl    (15%) — 450 примеров
    └── test.jsonl   (15%) — 450 примеров (НИКОГДА не используется при тренировке)
```

> **Термин: Data Leakage (утечка данных)** — когда информация из test/val попадает в train. В
> текущем проекте все вариации одного шаблона могут попасть в разные сплиты — модель "видит"
> почти тот же текст в train, что потом оценивается в val. **Это критический баг**.

**Решение**: Split должен быть **по шаблонам**, не по примерам. Все вариации одного шаблона
должны быть либо целиком в train, либо целиком в val/test.

#### Шаг 5: Валидация целостности

Перед тренировкой проверить:
- Нет дубликатов текстов.
- Все JSON в assistant-ответах валидны.
- Все category_id и subcategory_id существуют в `categories-service/categories.py`.
- Нет пустых formalized_text у важных примеров.
- theses всегда непустой массив у важных.

## 2. АНАЛИЗ КАЖДОЙ МОДЕЛИ

### 2.1 Модель 1: ImportanceClassifier (rubert-tiny2)

#### Что это и зачем

> **Термин: BERT (Bidirectional Encoder Representations from Transformers)** — архитектура
> трансформера-энкодера, предобученная на задаче маскированного языкового моделирования (MLM).
> Понимает контекст слова с обеих сторон.

**cointegrated/rubert-tiny2** — это дистиллированная версия BERT для русского языка:
- Размер: **29 MB** (312 hidden dim, 3 layers, 12 attention heads)
- Словарь: 83,828 токенов (BPE)
- Предобучена на русском тексте (Wikipedia, новости)

**Задача**: Бинарная классификация — "жалоба" (1) vs "не жалоба" (0)

**Архитектура fine-tune:**
```
[CLS] token embedding → 3 transformer layers → [CLS] hidden state → Linear(312, 2) → softmax → [0, 1]
```

> **Термин: Fine-tuning** — дообучение предобученной модели на downstream task (целевой задаче).
> Все веса модели обновляются под конкретную задачу с маленьким learning rate.

#### Как работает (код)

Файл `nlp-service/models/classifier.py`:
1. Загружает fine-tuned веса из `trained_models/classifier/` (или базовую модель).
2. `predict(text)` → токенизирует текст → прогоняет через модель → softmax → argmax.
3. Возвращает `(is_important: bool, confidence: float)`.

Файл `nlp-service/train_classifier.py`:
- Гиперпараметры: epochs=3, lr=2e-5, batch=32, max_len=256, val_split=0.15.
- Метрики: accuracy + F1 (binary).
- Сохранение: best model by F1.

#### Соответствие CLAUDE.md

CLAUDE.md говорит: "rubert-tiny2 (29MB), ~50ms на CPU, после fine-tune точность ~95%+" — **всё
корректно**, но **точность 95%+ обманчива** из-за дисбаланса 90/10 (см. раздел 1.2B).

#### Обнаруженные баги/рассогласования

- В `classifier.py:80` inference использует `max_length=512`, но тренировка (`train_classifier.py`)
  использует `max_len=256`. **Рассогласование** — тренируй на том же max_len что и в inference.

#### Как улучшить

1. **Class weights**: добавить `class_weight` в функцию потерь чтобы компенсировать дисбаланс:
   ```python
   class_weights = torch.tensor([9.0, 1.0])  # больший вес для неважных
   ```

2. **Focal Loss** вместо Cross-Entropy — лучше работает с дисбалансом:
   > **Термин: Focal Loss** — модификация CE loss, которая уменьшает вклад легко
   > классифицируемых примеров и фокусирует обучение на трудных случаях.
   > Формула: FL = -α(1-p)^γ * log(p)

3. **Early Stopping с patience**: текущий код загружает лучшую модель, но тренирует всегда все
   эпохи.

4. **Larger model**: заменить rubert-tiny2 на `ai-forever/ruBert-base` (711 MB) — точнее, но
   медленнее.

5. **Threshold tuning**: вместо argmax(probs) подбирать оптимальный порог confidence через
   PR-curve.

#### Как бенчмаркать

**Метрики для классификатора:**

| Метрика | Что измеряет | Зачем |
|---------|-------------|-------|
| **Accuracy** | % верных предсказаний | Бесполезна при дисбалансе |
| **Precision (important)** | из предсказанных important, сколько верных | Ложные тревоги |
| **Recall (important)** | из реальных important, сколько найдены | **Критично: нельзя пропускать** |
| **F1-score** | гармоническое среднее P и R | Баланс |
| **F1-macro** | среднее F1 по всем классам | Учитывает оба класса равно |
| **AUC-ROC** | площадь под ROC-кривой | Качество при разных порогах |
| **Confusion Matrix** | матрица ошибок 2×2 | Визуальное понимание ошибок |

> **Термин: Precision-Recall Trade-off** — увеличение одной метрики обычно снижает другую. В
> медицине: **Recall важнее Precision** — лучше лишний раз проверить, чем пропустить инцидент.

> **Термин: AUC-ROC (Area Under Receiver Operating Characteristic)** — метрика, не зависящая от
> порога решения. AUC=1.0 — идеальная модель, AUC=0.5 — случайное угадывание.

### 2.2 Модель 2: TextProcessor (rut5-base-multitask)

#### Что это и зачем

> **Термин: T5 (Text-to-Text Transfer Transformer)** — архитектура encoder-decoder, которая
> формулирует ВСЕ задачи NLP как "текст → текст". Вход: "переведи: Hello" → Выход: "Привет".

**cointegrated/rut5-base-multitask** — русская версия T5:
- Размер: **222 MB** (~220M параметров)
- Предобучена на множественных русскоязычных задачах (суммаризация, перефразирование, QA)
- Использует SentencePiece токенизатор

**Две задачи через prefix:**
1. `"формализуй: {текст}"` → медицинский формализованный текст
2. `"тезисы: {текст}"` → маркированный список ключевых тезисов

> **Термин: Prefix-based multitask** — подход T5, где тип задачи определяется текстовым
> префиксом. Одна модель = много задач.

#### Как работает (код)

Файл `nlp-service/models/seq2seq.py`:
- `_generate()` — beam search с num_beams=4, no_repeat_ngram_size=3
- `formalize(text)` → `_generate("формализуй: " + text, max_new_tokens=150)`
- `extract_theses(text)` → парсит `_generate("тезисы: " + text)` по `\n`, убирает маркеры

> **Термин: Beam Search** — алгоритм декодирования, который поддерживает top-K (num_beams)
> лучших частичных последовательностей на каждом шаге. Даёт более качественный текст, чем
> greedy search, но медленнее.

> **Термин: Teacher Forcing** — при обучении/evaluation модель получает **правильный**
> предыдущий токен на каждом шаге (а не свой собственный предсказанный). Это быстрее, но
> **не отражает реальное качество генерации** — в inference модель использует свои предсказания.

#### Обнаруженные баги/рассогласования

- CLAUDE.md nlp-service указывает `--max-src 256 --max-tgt 128`, но в коде
  `train_seq2seq.py:208-209` default стоит **128/64**. **Расхождение!** Рекомендую использовать
  256/128 как написано в CLAUDE.md.

- `predict_with_generate=False` — означает что evaluation использует teacher forcing, а не
  реальную генерацию. Метрика token_accuracy на val **завышена** и не отражает реальное
  качество.

#### Как улучшить

1. **ROUGE метрики** вместо token_accuracy:
   > **Термин: ROUGE (Recall-Oriented Understudy for Gisting Evaluation)** — семейство метрик:
   > - **ROUGE-1**: совпадение отдельных слов (unigrams)
   > - **ROUGE-2**: совпадение пар слов (bigrams)
   > - **ROUGE-L**: наибольшая общая подпоследовательность (LCS)

2. **BERTScore** — семантическая метрика:
   > **Термин: BERTScore** — метрика, которая сравнивает тексты через embedding similarity. В
   > отличие от ROUGE, понимает синонимы и перефразирование.

3. **Раздельные модели** для формализации и тезисов: одна модель = два конкурирующих задания.

4. **predict_with_generate=True** при финальном eval для честной оценки качества генерации.

5. **Увеличить max_tgt** до 128 — некоторые формализации могут быть длиннее 64 токенов.

#### Как бенчмаркать

1. **ROUGE-1, ROUGE-2, ROUGE-L** по test set (отдельно для формализации и тезисов)
2. **BERTScore F1** — `pip install bert-score`
3. **Человеческая оценка**: 50 примеров, шкала 1-5 по: (а) фактическая корректность, (б)
   полнота, (в) стиль
4. **Сравнение с LLM**: прогнать те же примеры через Qwen, сравнить ROUGE/BERTScore

### 2.3 Модель 3: CategoryMatcher (MiniLM)

#### Что это и зачем

> **Термин: Sentence Embeddings** — векторные представления целых предложений в едином
> пространстве, где семантически похожие тексты имеют близкие векторы.

**paraphrase-multilingual-MiniLM-L12-v2** — мультиязычная sentence-transformer:
- Размер: **117 MB** (12 layers, 384 hidden dim)
- Обучена на 50+ языках через knowledge distillation от большой модели
- Создаёт 384-мерные эмбеддинги

> **Термин: Knowledge Distillation** — передача знаний от большой модели (teacher) к маленькой
> (student). MiniLM обучена имитировать выходы полноразмерной multilingual-mpnet.

> **Термин: Zero-shot Classification** — классификация без обучения на целевом датасете. Модель
> использует общие семантические знания для сопоставления текста с описаниями классов.

#### Как работает (код)

Файл `nlp-service/models/similarity.py`:

**Алгоритм (subcategory-first):**
1. При загрузке категорий из NATS: encode все `"name: description"` → матрицы эмбеддингов
2. На запросе: encode `[text, formalized_text]` → усреднение → нормализация
3. Cosine similarity со ВСЕМИ подкатегориями → argmax → лучшая подкатегория
4. Родительская категория = категория этой подкатегории

> **Термин: Cosine Similarity** — мера сходства двух векторов через косинус угла между ними.
> Значение от -1 (противоположные) до 1 (идентичные).
> cos(A,B) = (A·B) / (||A|| × ||B||)

#### Как улучшить

1. **Добавить threshold**: сейчас модель ВСЕГДА выбирает лучшую подкатегорию, даже если
   similarity = 0.15. Нужен минимальный порог (например 0.3) — если ниже, вернуть `(None, None)`.

2. **Fine-tune MiniLM** на датасете через Contrastive Learning:
   > **Термин: Contrastive Learning** — обучение модели, чтобы похожие примеры были близко, а
   > непохожие далеко. Варианты: Triplet Loss, Multiple Negatives Ranking Loss.

3. **Enriched category descriptions**: добавить в описания категорий примеры жалоб.

4. **Cross-encoder reranker**: после biencoder top-5 пропустить через cross-encoder для точного
   ранжирования.
   > **Термин: Bi-encoder vs Cross-encoder** — bi-encoder кодирует текст и класс отдельно
   > (быстро, но менее точно). Cross-encoder обрабатывает пару совместно (медленнее, но точнее).

#### Как бенчмаркать

1. **Category Accuracy**: % правильно определённых категорий (7 классов)
2. **Subcategory Accuracy**: % правильных подкатегорий (21 класс)
3. **Top-K Accuracy**: правильный ответ в top-3 / top-5
4. **Confusion Matrix 7×7** — покажет, какие пары категорий путаются
5. **Средний cosine similarity**: score для правильных vs неправильных

> **Термин: MRR (Mean Reciprocal Rank)** — если правильный ответ на позиции k в ранжированном
> списке, его вклад = 1/k. MRR=1 означает, что правильный ответ всегда на первом месте.

### 2.4 Модель 4: Qwen2.5-3B (llm-service)

#### Что это и зачем

> **Термин: LLM (Large Language Model)** — большая языковая модель, обученная на огромном
> текстовом корпусе генерировать текст авторегрессионно (token за token). Может выполнять
> множество задач через промпт.

**Qwen2.5-3B** (от Alibaba):
- Параметры: **3.1 млрд (3B)**
- Контекст: 32K токенов
- Языки: мультиязычная (сильная на китайском, английском, русском)
- Формат: GGUF Q4_K_M (квантизация 4-бит) — ~1.9 GB
- Inference через Ollama

> **Термин: Квантизация (Quantization)** — сжатие весов модели из float32 (4 байта) в int4
> (0.5 байта). Q4_K_M — 4-битная квантизация с k-quants (k-means clustering весов). Снижает
> размер в ~4x с минимальной потерей качества.

#### Как работает

1. Backend декорирует жалобу категориями из NATS
2. Формирует system prompt + user message с категориями
3. Один вызов к Ollama API → LLM генерирует полный JSON
4. Парсится как ответ

#### Как улучшить

1. **Few-shot prompting**: добавить 2-3 примера в system prompt.
   > **Термин: Few-shot Learning** — предоставление модели нескольких примеров "вход → выход"
   > прямо в промпте. В отличие от fine-tuning, не меняет веса модели.

2. **Structured output**: JSON mode Ollama (`"format": "json"`) для гарантии валидного JSON.

3. **Temperature**: для классификации лучше `temperature=0.1` (более детерминированный).

4. **Fine-tune Qwen** через LoRA:
   > **Термин: LoRA (Low-Rank Adaptation)** — метод fine-tuning, который обучает не все веса, а
   > маленькие дополнительные матрицы (rank=8-64). Требует на порядок меньше памяти и времени.

#### Как бенчмаркать

```bash
python3 test_llm.py --n 100 --seed 42           # 100 важных примеров
python3 test_llm.py --n 50 --not-important --seed 42  # 50 неважных
```

| Метрика | Что | Зачем |
|---------|-----|-------|
| JSON validity rate | % валидного JSON | Базовое — невалидный JSON = бесполезный ответ |
| is_important accuracy | Точность бинарной классификации | Сравнение с rubert-tiny2 |
| Category accuracy | % верных категорий | Сравнение с MiniLM |
| Subcategory accuracy | % верных подкатегорий | Детальное сравнение |
| ROUGE-L (formalized) | Качество формализации | Сравнение с rut5 |
| Latency (p50, p95) | Время ответа | Практическая применимость |

## 3. ОЦЕНКА ПОДХОДА ДЛЯ ДИПЛОМА: LLM vs NLP Pipeline

### 3.1 Почему это сильная тема

Сравнение "LLM monolith vs ансамбль маленьких специализированных моделей" — **актуальная и
практически значимая тема** в NLP 2024-2026:

1. **Актуальность**: индустрия решает именно этот вопрос — когда LLM оправдана, а когда хватает
   классических NLP моделей.
2. **Практическая ценность**: медицинская сфера, реальная задача.
3. **Многоаспектность**: качество, скорость, ресурсы, стоимость.
4. **Два контрастных подхода**: один вызов LLM vs пайплайн из 3 специализированных моделей.

### 3.3 Что добавить для усиления

#### A. Третий подход — Hybrid

Для диплома сильнее показать **3 подхода**:

1. **LLM-only** (текущий llm-service)
2. **NLP-pipeline** (текущий nlp-service)
3. **Hybrid**: NLP-pipeline делает быструю классификацию, а LLM вызывается только для сложных
   случаев (confidence < threshold)

Это показывает инженерную зрелость и понимание trade-offs.

#### B. Статистическая значимость

> **Термин: Статистическая значимость** — насколько мы уверены, что различие между двумя
> моделями не случайно.

- **McNemar's test** — для сравнения двух классификаторов на одном датасете
- **Bootstrap confidence intervals** — 95% доверительные интервалы для метрик
- **Paired t-test** или **Wilcoxon signed-rank** — для ROUGE/latency

Без этого рецензент может сказать: "Откуда вы знаете, что разница в 2% accuracy не случайна?"

#### C. Человеческая оценка (Human Evaluation)

- 50-100 примеров оценены 2-3 экспертами (врачи или медсёстры)
- Шкала: 1-5 по каждому полю (формализация, тезисы, категория)
- **Inter-annotator agreement** (согласованность оценщиков):
  > **Термин: Cohen's Kappa (κ)** — мера согласованности оценщиков с поправкой на случайное
  > согласие. κ=1 — полное согласие, κ>0.6 — хорошее, κ<0.2 — плохое.

#### D. Ablation Study

> **Термин: Ablation Study** — систематическое отключение компонентов для понимания вклада
> каждого.

Для NLP-pipeline:
1. Base rubert + base rut5 + MiniLM (baseline)
2. Fine-tuned rubert + base rut5 + MiniLM
3. Fine-tuned rubert + fine-tuned rut5 + MiniLM
4. Только fine-tuned rubert (без формализации, matcher по raw text)

Это покажет, какой компонент даёт наибольший прирост.

#### E. Error Analysis

Для каждого подхода проанализировать:
- **Типы ошибок**: какие категории путаются? На каких текстах ошибки?
- **Корреляция ошибок**: ошибаются ли подходы на одних и тех же примерах?
- **Каскадный эффект** в NLP-pipeline: если классификатор ошибся (is_important=False для
  реальной жалобы), весь остальной пайплайн не запускается. В LLM такого нет — это важное
  архитектурное различие.

## 4. БЕНЧМАРКИ ДО И ПОСЛЕ ТРЕНИРОВКИ

### 4.1 Ключевые термины

| Термин | Определение |
|--------|------------|
| **Benchmark** | Стандартизированный тест для измерения производительности модели |
| **Baseline** | Начальная точка отсчёта до улучшений |
| **Precision** | TP / (TP + FP) — из предсказанных positive, сколько верных |
| **Recall** | TP / (TP + FN) — из реальных positive, сколько найдены |
| **F1-score** | 2 * P * R / (P + R) — гармоническое среднее |
| **Accuracy** | (TP + TN) / total — общая доля верных |
| **AUC-ROC** | Площадь под кривой TPR vs FPR при разных порогах |

| **MCC** | Matthews Correlation Coefficient — лучшая метрика для binary при дисбалансе |

## 5. РЕЗЮМЕ КЛЮЧЕВЫХ НАХОДОК

### Проблемы датасета (критические)
1. **Data Leakage**: вариации одного шаблона попадают в train и val одновременно — split должен
   быть по шаблонам, не по примерам.
2. **Дисбаланс 90:10** — нужна балансировка или weighted loss.
3. **120 уникальных жалоб** — слишком мало для обобщения; нужна аугментация.
4. **Нет test set** — только train+val; необходим hold-out test.

### Баги в коде
1. **train_seq2seq.py**: default `--max-src 128 --max-tgt 64` не совпадает с CLAUDE.md (256/128).
2. **classifier.py**: inference использует max_length=512, тренировка — 256. Надо унифицировать.
3. **train_seq2seq.py**: `predict_with_generate=False` — завышает метрику на val.

### Сильные стороны проекта
1. Архитектура с NATS KV для динамических категорий — правильное решение.
2. CategoryMatcher zero-shot — элегантно, без переобучения на категориях.
3. Два параллельных подхода — идеально для дипломного сравнения.
4. Docker Compose с правильным порядком запуска через depends_on + healthcheck.

### Приоритеты для диплома
1. Исправить data leakage (split по шаблонам) — это №1.
2. Создать hold-out test set — обязательно.
3. Запустить baselines до fine-tune — зафиксировать точку отсчёта.
4. Обучить обе модели, измерить ROUGE/F1.
5. Прогнать Qwen на том же test set — финальное сравнение.
6. Добавить latency и memory в таблицу сравнения.
