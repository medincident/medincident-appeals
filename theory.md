## 1. Архитектура системы

### Два параллельных подхода

Система реализует две независимые стратегии обработки обращений пациентов:

**Подход 1 — LLM (end-to-end):** одна большая модель (Qwen2.5-3B) получает текст жалобы + список категорий в промпте и генерирует полный JSON-ответ за один вызов. Zero-shot — не требует обучения на датасете.

**Подход 2 — NLP-pipeline (3 модели):** три специализированные модели работают последовательно, каждая решает свою задачу:

```
Текст жалобы
    |
    v
[ImportanceClassifier] -- rubert-tiny2 (29 MB)
    |                      Бинарная классификация: важно / не важно
    |
    +-- Не важно --> ранний ответ (is_important=false)
    |
    +-- Важно --> продолжить
         |
    +----+----+
    |         |
    v         v
[TextProcessor]     [TextProcessor]      -- rut5 (222 MB, shared)
 формализуй:         тезисы:
    |                    |
    v                    v
formalized_text      theses[]
    |
    v
[CategoryMatcher] -- MiniLM (117 MB)
    |                 Cosine similarity, zero-shot
    v
category + subcategory
    |
    v
Итоговый JSON
```

### Почему два подхода

Суть диплома — **сравнение**: LLM (универсальная модель, тяжёлая, точная) vs NLP-pipeline (легковесные специализированные модели, быстрые, требуют обучения). Это позволяет ответить на вопрос: можно ли заменить LLM на набор мелких моделей без значительной потери качества, выиграв в скорости и ресурсах.

## 2. Модель 1: ImportanceClassifier (rubert-tiny2)

### Что такое BERT

**BERT (Bidirectional Encoder Representations from Transformers)** — архитектура трансформера-энкодера. В отличие от GPT (который читает текст слева направо), BERT видит контекст с обеих сторон одновременно. Это достигается через **Masked Language Modeling (MLM)** при предобучении: случайные токены маскируются, и модель предсказывает их по окружающему контексту.

### rubert-tiny2: зачем именно эта модель

`cointegrated/rubert-tiny2` — дистиллированная версия BERT для русского языка:

| Параметр | Значение |
|----------|----------|
| Размер | 29 MB |
| Hidden dim | 312 |
| Layers | 3 (vs 12 в полном BERT) |
| Attention heads | 12 |
| Словарь | 83 828 токенов (BPE) |
| Предобучение | Русская Wikipedia + новости |

**Почему rubert-tiny2, а не bert-base-multilingual:**
- В 25 раз меньше (29 MB vs 711 MB)
- Инференс ~50 мс vs ~200 мс на CPU
- Специализирован на русском (а не 100+ языков)
- Для бинарной классификации коротких текстов (avg 101 символ) избыточная модель не нужна

### Архитектура fine-tune

```
Input: "упал с кровати ночью"
    |
    v
[Tokenizer] --> [CLS] уп ##ал с кров ##ати ночь ##ю [SEP] [PAD]...
    |
    v
[3 Transformer Layers] --> hidden states (312-dim per token)
    |
    v
[CLS] hidden state (312-dim) -- агрегирует информацию всего предложения
    |
    v
[Linear(312, 2)] --> logits: [score_not_imp, score_imp]
    |
    v
[Softmax] --> probabilities: [0.15, 0.85]
    |
    v
argmax --> label=1 ("important"), confidence=0.85
```

**Ключевые моменты:**
- `[CLS]` токен — специальный токен в начале, его hidden state используется как представление всего предложения
- `Linear(312, 2)` — классификационная голова, добавляется поверх BERT. При загрузке базовой модели эти веса **случайные** (поэтому baseline ~52% F1)
- Fine-tune обновляет **все** веса модели (и BERT layers, и классификационную голову) с маленьким learning rate

### Токенизация

BERT использует **WordPiece** (подвид BPE): разбивает слова на подслова.

```
"упал" --> ["уп", "##ал"]
"кровати" --> ["кров", "##ати"]
"пожалуйста" --> ["пожал", "##уйста"]
```

`##` означает что подслово продолжает предыдущее (не начинает новое слово).

**Параметры токенизации:**
- `max_length=256` при обучении, `max_length=512` при инференсе
- `truncation=True` — обрезает длинные тексты (справа)
- `padding=True` — дополняет короткие [PAD] токенами до длины батча

## 3. Модель 2: TextProcessor (rut5-base-multitask)

### Что такое T5

**T5 (Text-to-Text Transfer Transformer)** — encoder-decoder архитектура, которая формулирует ВСЕ задачи NLP как "текст-на-входе → текст-на-выходе":

```
Перевод:    "translate: Hello"       --> "Привет"
Суммаризация: "summarize: длинный текст" --> "краткий текст"
Классификация: "classify: отзыв"     --> "positive"
```

В отличие от BERT (только encoder, выдаёт вектор), T5 **генерирует текст** токен за токеном.

### rut5-base-multitask

`cointegrated/rut5-base-multitask` — русская версия T5, предобученная на множественных задачах:

| Параметр | Значение |
|----------|----------|
| Размер | 222 MB (~220M параметров) |
| Архитектура | Encoder-Decoder (T5) |
| Токенизатор | SentencePiece (32 000 токенов) |
| Предобучение | Суммаризация, перефразирование, QA на русском |

### Две задачи через prefix

Одна модель решает две задачи, различая их по текстовому префиксу:

```
Задача 1 (формализация):
  Вход:  "формализуй: упал с кровати ночью, ударился головой"
  Выход: "Пациент сообщает о падении с кровати в ночное время с травмой головы."

Задача 2 (тезисы):
  Вход:  "тезисы: упал с кровати ночью, ударился головой"
  Выход: "- Падение с кровати в ночное время\n- Травма головы"
```

**Почему одна модель на две задачи:** Экономия памяти — 222 MB вместо 444 MB. Модель учится различать задачи по префиксу. Это стандартный подход T5 (prefix-based multitask learning).

### Генерация текста: Beam Search

При инференсе модель генерирует текст токен за токеном. Есть несколько стратегий:

**Greedy Search** (жадный): на каждом шаге выбирает самый вероятный токен. Быстро, но не оптимально — первый выбор может завести в плохую ветку.

**Beam Search** (лучевой поиск): поддерживает `num_beams` лучших гипотез параллельно:

```
Шаг 1: "Пациент" (beam 1), "Больной" (beam 2), "В" (beam 3), "У" (beam 4)
Шаг 2: Для каждого beam рассматриваем все продолжения, оставляем top-4
        "Пациент сообщает" (0.9), "Пациент упал" (0.85), "Больной упал" (0.7), ...
Шаг 3: Продолжаем до [EOS] или max_length
Результат: лучший полный beam
```

**Параметры генерации в проекте:**
```python
num_beams=4              # 4 параллельных гипотезы
max_new_tokens=150       # макс 150 новых токенов (формализация)
early_stopping=True      # остановка когда все beams достигли [EOS]
no_repeat_ngram_size=3   # запрет повторения 3-грамм ("и потом и потом и потом")
```

### Teacher Forcing vs Autoregressive Generation

Два режима оценки модели:

**Teacher Forcing** (при обучении): на каждом шаге модель получает **правильный** предыдущий токен. Если эталон "Пациент упал", на шаге 2 модель всегда видит "Пациент" (даже если предсказала "Больной"). Это ускоряет обучение, но **завышает** метрики — модель не учится исправлять свои ошибки.

**Autoregressive Generation** (при инференсе): модель использует **свои собственные** предсказания. Если предсказала "Больной" вместо "Пациент", следующий шаг будет от "Больной...". Ошибки накапливаются (exposure bias).

В проекте: `predict_with_generate=True` — при evaluation используется реальная генерация (beam search), а не teacher forcing. Это даёт **честные** метрики.

## 4. Модель 3: CategoryMatcher (MiniLM)

### Sentence Embeddings

Sentence Transformers преобразуют **целые предложения** в векторы фиксированной размерности. Семантически похожие предложения имеют близкие векторы.

```
"Пациент упал с кровати"  --> [0.12, -0.34, 0.56, ..., 0.78]  (384 dim)
"Больной свалился с койки" --> [0.13, -0.33, 0.55, ..., 0.77]  (384 dim)
"Холодная еда в палате"   --> [-0.45, 0.67, -0.12, ..., 0.34] (384 dim)

cosine_similarity(первый, второй) ≈ 0.95  (семантически близки)
cosine_similarity(первый, третий) ≈ 0.15  (семантически далеки)
```

### MiniLM-L12-v2

`paraphrase-multilingual-MiniLM-L12-v2` — мультиязычная модель sentence-transformers:

| Параметр | Значение |
|----------|----------|
| Размер | 117 MB |
| Layers | 12 |
| Hidden dim | 384 |
| Языки | 50+ (включая русский) |
| Обучение | Knowledge distillation от полноразмерной модели |

**Knowledge Distillation** (дистилляция знаний) — метод сжатия модели: большая модель (teacher) обучает маленькую (student) воспроизводить свои выходы. MiniLM обучена имитировать multilingual-mpnet (в 3 раза больше).

### Zero-shot классификация

Модель **не обучается** на конкретных категориях. Вместо этого:
1. Категории загружаются из NATS KV как текст
2. Текст каждой категории/подкатегории кодируется в вектор
3. Жалоба кодируется в вектор
4. Cosine similarity находит ближайшую категорию

```
Категории (закодированы при старте):
  "Падения пациентов в МО: ..."           --> vec_1 (384-dim)
  "Ошибка при введении препарата: ..."    --> vec_2 (384-dim)
  "Нарушение санитарных норм: ..."        --> vec_3 (384-dim)
  ...

Жалоба:
  "упал с кровати ночью"                  --> query_vec (384-dim)

Результат:
  similarity(query_vec, vec_1) = 0.82  <-- WINNER
  similarity(query_vec, vec_2) = 0.15
  similarity(query_vec, vec_3) = 0.21
```

### Cosine Similarity: математика

Cosine similarity измеряет угол между двумя векторами:

```
cos(a, b) = (a . b) / (|a| * |b|)
```

Где:
- `a . b` — скалярное произведение
- `|a|`, `|b|` — L2-нормы (длины) векторов

Результат: от -1 (противоположные) до +1 (идентичные).

**Оптимизация в коде:** векторы заранее L2-нормализуются (`normalize_embeddings=True`), после чего cosine similarity = просто скалярное произведение:

```python
# После нормализации: |a| = |b| = 1
cos(a, b) = a . b / (1 * 1) = a . b
# Матричное умножение для всех категорий разом:
similarities = category_matrix @ query_vector  # shape: (N_categories,)
```

### Алгоритм матчинга: subcategory-first

```python
# 1. Кодируем жалобу (оригинал + формализация)
query = average(encode(original_text), encode(formalized_text))

# 2. Cosine similarity со ВСЕМИ подкатегориями
similarities = subcategory_embeddings @ query  # (22 подкатегории,)

# 3. Лучшая подкатегория
best_sub_idx = argmax(similarities)
best_subcategory = subcategories[best_sub_idx]

# 4. Категория = родитель подкатегории
best_category = parent_of(best_subcategory)
```

**Почему average оригинала и формализации?** Оригинал содержит специфические фразы пациента ("грохнулся"), формализация — медицинские термины ("падение"). Усреднение захватывает оба сигнала.

**Почему subcategory-first?** Подкатегории более специфичны → матчинг точнее. Категория однозначно определяется по подкатегории (parent lookup).

## 5. LLM-подход: Qwen2.5-3B

### Модель

| Параметр | Значение |
|----------|----------|
| Модель | Qwen2.5-3B (Alibaba Cloud) |
| Параметры | 3.1 миллиарда |
| Квантизация | Q4_K_M (4-bit) |
| Размер файла | ~1.9 GB |
| Контекст | 32K токенов |
| Runtime | Ollama (Docker контейнер) |
| Latency CPU | ~104-130 сек/запрос |
| Latency GPU | ~3-5 сек/запрос |

### Квантизация (Q4_K_M)

Квантизация — сжатие весов модели из 32-bit float в 4-bit integer:

```
Оригинал (FP32): 3.1B параметров * 4 байта = ~12 GB
Q4_K_M (4-bit):  3.1B параметров * 0.5 байта = ~1.9 GB (сжатие в 6x)
```

**Q4_K_M** — один из лучших 4-bit форматов: "K" означает k-means кластеризацию весов, "M" — medium quality. Потеря качества минимальна (~1-2% на бенчмарках).

### Промпт-инжиниринг

LLM получает **system prompt** + **user message** с категориями:

```
System: "Проанализируй обращение и верни JSON по схеме... 
         is_important=true только если жалоба на здоровье..."

User: "Обращение пациента:
       упал с кровати ночью, ударился головой
       
       Доступные категории инцидентов:
       - [cat_1] Организация ухода за пациентами
           * [sub_1_1] Падения пациентов в МО
           * [sub_1_2] Повреждения кожных покровов
       - [cat_2] Лекарственная безопасность
       ..."
```

**Динамические категории:** список категорий передаётся в каждом запросе (из NATS KV), не зашит в модель. Если категории изменятся — модель автоматически использует новые.

### Zero-shot vs Fine-tuned NLP

LLM работает **zero-shot** — не обучается на датасете, использует знания из предобучения. NLP-модели **fine-tuned** — дообучены на 3000 примерах. Это "нечестное" сравнение в пользу NLP, но отражает реальный сценарий: LLM можно запустить сразу, а NLP требует подготовки.

## 6. Обучение: классификатор

### Функция потерь: Cross-Entropy Loss

Для бинарной классификации:

```
CE = -[y * log(p) + (1-y) * log(1-p)]

Где:
  y = истинная метка (0 или 1)
  p = предсказанная вероятность класса 1
```

Если модель предсказывает p=0.9 для примера с y=1: CE = -log(0.9) = 0.105 (маленькая ошибка).
Если предсказывает p=0.1 для y=1: CE = -log(0.1) = 2.303 (большая ошибка).

### Оптимизатор: AdamW

**AdamW** — Adam с decoupled weight decay:
- Адаптивный learning rate для каждого параметра
- Momentum (beta1=0.9): сглаживание градиентов
- Velocity (beta2=0.999): нормализация по дисперсии градиентов
- Weight decay=0.01: L2-регуляризация (предотвращает переобучение)

### Learning Rate Schedule

```
       lr
  2e-5 |    /-------\
       |   /         \
       |  /           \
  0    | /             \
       +--+---+---+---+---> steps
         warmup  training  decay

warmup_ratio=0.1: первые 10% шагов lr линейно растёт от 0 до 2e-5
Остальные 90%: lr линейно убывает до 0
```

**Зачем warmup?** Без разогрева большой начальный lr может "сломать" предобученные веса BERT.

### Гиперпараметры

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| epochs | 3 | Достаточно для 3000 примеров, больше — риск переобучения |
| lr | 2e-5 | Стандарт для BERT fine-tune (оригинальная статья) |
| batch_size | 32 | Баланс скорости и стабильности градиентов |
| max_len | 256 | Средний текст 101 символ ≈ 50-70 токенов, 256 с запасом |
| weight_decay | 0.01 | Лёгкая регуляризация |
| warmup_ratio | 0.1 | 10% шагов на разогрев |

### Выбор лучшей модели

```
metric_for_best_model = "f1"
load_best_model_at_end = True
```

После каждой эпохи модель оценивается на val set. Сохраняется чекпоинт с лучшим F1. В конце обучения восстанавливается лучший чекпоинт.

**Почему F1, а не accuracy?** При дисбалансе 75/25 модель может всегда предсказывать "important" и получить accuracy=75%. F1 учитывает и precision и recall, штрафуя за такое поведение.

## 7. Обучение: seq2seq

### Двойная задача из одного датасета

Каждый important пример порождает 2 обучающих пары:

```
Пример: "упал с кровати ночью" -> {"formalized_text": "Пациент упал...", "theses": [...]}

Пара 1: "формализуй: упал с кровати ночью"  -->  "Пациент упал с кровати в ночное время."
Пара 2: "тезисы: упал с кровати ночью"      -->  "- Падение с кровати\n- Ночное время"
```

Итого: ~2250 important * 2 = ~4500 пар для обучения.

### Loss: Seq2Seq Cross-Entropy

В seq2seq loss считается по каждому токену выхода:

```
Loss = mean_over_tokens(-log(p(правильный_токен_i | предыдущие_токены)))

Пример: target = "Пациент упал"
  Шаг 1: p("Пациент" | [START]) = 0.7  --> loss_1 = -log(0.7) = 0.36
  Шаг 2: p("упал" | "Пациент")  = 0.5  --> loss_2 = -log(0.5) = 0.69
  Total loss = (0.36 + 0.69) / 2 = 0.52
```

Токены с label=-100 (padding) исключаются из loss (маска).

### DataCollatorForSeq2Seq

```python
collator = DataCollatorForSeq2Seq(tokenizer, model=model, padding=True)
```

**Зачем?** Вместо padding всего датасета до максимальной длины, коллатор паддит каждый батч до максимальной длины **внутри батча**. Экономит память и ускоряет обучение.

### Гиперпараметры

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| epochs | 5 | Больше чем у classifier: генерация сложнее, нужно больше эпох |
| lr | 5e-5 | Выше чем BERT: T5 лучше принимает большой lr |
| batch_size | 16 | Меньше чем classifier из-за encoder-decoder (2x память) |
| max_src | 256 | Длина входа (complaint + prefix) |
| max_tgt | 128 | Длина выхода (formalized text / theses) |
| generation_num_beams | 4 | Beam search при eval |
| warmup_ratio | 0.05 | Меньше чем classifier: T5 стабильнее |

## 8. Метрики оценки

### Классификация: Precision, Recall, F1

```
                    Predicted
                   Imp    Not-Imp
Actual  Imp    [  TP  |  FN  ]
        Not    [  FP  |  TN  ]

Precision = TP / (TP + FP)   -- "из предсказанных важных, сколько действительно важных?"
Recall    = TP / (TP + FN)   -- "из реально важных, сколько мы нашли?"
F1        = 2 * P * R / (P + R) -- гармоническое среднее
```

**Precision-Recall Trade-off:** повышение recall (находим больше важных) обычно снижает precision (появляются ложные тревоги). В медицине **recall важнее** — лучше проверить лишний раз, чем пропустить инцидент.

**F1-macro:** среднее F1 по всем классам. Учитывает оба класса равноправно, даже при дисбалансе 75/25.

### AUC-ROC

Area Under Receiver Operating Characteristic. Измеряет качество модели при **всех** порогах решения:

```
Порог 0.5: "important" если confidence > 0.5
Порог 0.7: "important" если confidence > 0.7 (строже, меньше false positives)
Порог 0.3: "important" если confidence > 0.3 (мягче, больше true positives)

AUC = площадь под кривой TPR(FPR) при всех порогах
AUC = 1.0 -- идеальная модель
AUC = 0.5 -- случайное угадывание
```

### Генерация: ROUGE

**ROUGE (Recall-Oriented Understudy for Gisting Evaluation)** — стандартные метрики для суммаризации:

```
Эталон:      "Пациент упал с кровати в ночное время"
Предсказание: "Пациент упал с кровати ночью"

ROUGE-1 (unigrams):
  Совпавшие: {пациент, упал, с, кровати, ночь(ю/ое)}
  Recall = совпавших / слов_в_эталоне
  Precision = совпавших / слов_в_предсказании
  F1 = гармоническое среднее

ROUGE-2 (bigrams):
  Эталон: {"пациент упал", "упал с", "с кровати", "кровати в", "в ночное", "ночное время"}
  Предсказание: {"пациент упал", "упал с", "с кровати", "кровати ночью"}
  Меньше совпадений -> ROUGE-2 < ROUGE-1

ROUGE-L (longest common subsequence):
  LCS("Пациент упал с кровати в ночное время", "Пациент упал с кровати ночью")
  = "Пациент упал с кровати" (4 слова)
  Измеряет структурное сходство (порядок слов сохранён)
```

**Для русского:** стандартный tokenizer rouge_score не работает с кириллицей. Используется whitespace tokenizer (разделение по пробелам).

### Генерация: BERTScore

**BERTScore** — семантическая метрика через embedding similarity. В отличие от ROUGE (сравнивает слова), BERTScore сравнивает **смыслы**:

```
"Пациент упал" и "Больной свалился" -> ROUGE-1 = 0.0 (разные слова)
                                    -> BERTScore > 0.8 (одинаковый смысл)
```

Работает через:
1. Кодирование обоих текстов через BERT
2. Matching каждого токена с ближайшим в другом тексте
3. Precision, Recall, F1 на уровне эмбеддингов

**Недостаток:** медленный на CPU (~2-5 сек/батч), поэтому используется только при финальной оценке.

## 9. Аугментация данных

### Зачем нужна аугментация

Датасет синтетический: 199 шаблонов, каждый порождает ~15 вариаций. Без аугментации модель **запоминает фразы** вместо обучения общим закономерностям (overfitting).

### Механизмы вариативности

**1. Преамбулы + суффиксы** (комбинаторные):
```
"" + ядро + ""                         -- голое ядро
"Здравствуйте! " + ядро + " Прошу принять меры."  -- вежливое
"Срочно! " + ядро + " Когда это исправят?"         -- требовательное
```
15 x 15 = 225 комбинаций.

**2. Синонимические замены** (лексические, ~30% вероятность):
```
"упал" -> "свалился" / "грохнулся" / "рухнул"
"медсестра" -> "сестра" / "сестричка"
"грубо" -> "по-хамски" / "нагрубила"
```
Делают ядро жалобы уникальным, не только обёртку.

**3. Разговорные вставки** (~20%):
```
"ну упал с кровати..."
"короче медсестра нагрубила..."
"блин таблетку не ту дали..."
```
Имитация реального стиля пациентов.

**4. Стилевые обёртки** (~15%):
```
"Я в шоке! ... Это просто ужас!"       -- эмоциональный
"Довожу до вашего сведения: ..."        -- формальный
"СРОЧНО! ...!!!"                       -- паникующий
"Пишу уже третий раз: ..."             -- повторное обращение
```
Учит модель распознавать жалобы **независимо от стиля**.

**5. Опечатки** (28 паттернов, ~30%):
```
Фонетические: "что" -> "чта", "помогите" -> "помагите"
Пропуск букв: "которая" -> "котрая"
Слипшиеся:    "не дали" -> "недали"
```
Имитация реального набора текста с телефона.

## 10. Data Leakage и стратегия split

### Проблема

Шаблон порождает ~15 вариаций с одинаковым ядром:
```
imp_5: "упал с кровати ночью..."  + "Прошу принять меры."     -- вариация 1
imp_5: "упал с кровати ночью..."  + "Это недопустимо."        -- вариация 2
imp_5: "Здравствуйте! упал с кровати ночью..."                -- вариация 3
```

При случайном split вариация 1 попадает в train, вариация 2 — в val. Модель видит почти тот же текст в train, что оценивается в val. **Метрики завышены**, реальное обобщение не измерено.

### Решение: split по template_id

```
199 шаблонов:
  141 шаблонов (все их вариации) --> train  (~2133 примеров)
   29 шаблонов (все их вариации) --> val    (~420 примеров)
   29 шаблонов (все их вариации) --> test   (~447 примеров)
```

Все вариации одного шаблона целиком в одном сплите. Модель в val/test видит **новые ядра жалоб**, которых не было в train. Это честная оценка обобщения.

### Hold-out test set

- **Train** — для обучения модели
- **Val** — для выбора лучшего чекпоинта (после каждой эпохи)
- **Test** — **никогда** не используется при обучении. Только для финального сравнения NLP vs LLM в дипломе.

## 11. Инференс-пайплайн

### NLP-pipeline: полный путь запроса

```python
POST /analyze {"text": "упал с кровати ночью"}

# Шаг 1: Классификация важности (~50 мс)
is_important=True, confidence=0.92

# Шаг 2: Формализация (~250 мс)
formalized = "Пациент сообщает о падении с кровати в ночное время."

# Шаг 3: Тезисы (~250 мс)
theses = ["Падение с кровати в ночное время", "Отсутствие помощи"]

# Шаг 4: Категория (~50 мс)
category = {"id": "cat_1", "name": "Организация ухода за пациентами"}
subcategory = {"id": "sub_1_1", "name": "Падения пациентов в МО"}

# Итого: ~600 мс на CPU
```

### LLM: полный путь запроса

```python
POST /v1/chat/completions
  system: "Проанализируй обращение... JSON-схема..."
  user: "Обращение: упал с кровати ночью\n\nКатегории: [cat_1]..."

# Один вызов: ~104 000 мс CPU / ~4 000 мс GPU
# Выход: полный JSON (is_important, formalized_text, theses, category, subcategory)
```

## 12. Сравнение подходов

| Аспект | NLP-pipeline | LLM (Qwen) |
|--------|-------------|-------------|
| **Архитектура** | 3 модели, pipeline | 1 модель, end-to-end |
| **Суммарный размер** | ~370 MB | ~1.9 GB |
| **Latency CPU** | ~600 мс | ~104 000 мс |
| **Latency GPU** | ~100 мс | ~4 000 мс |
| **RAM** | ~400 MB | ~4 GB |
| **Fine-tune** | Обязателен | Опционален |
| **Качество без обучения** | Низкое (F1=0.52) | Высокое (zero-shot) |
| **Качество с обучением** | Высокое (цель F1>0.90) | N/A в проекте |
| **Новые категории** | Автоматически (embedding) | Через промпт |
| **Новые типы жалоб** | Нужен fine-tune | Обобщает из предобучения |
| **GPU** | Не нужен | Желателен (130x ускорение) |
| **Масштабирование** | Горизонтальное (stateless) | Вертикальное (GPU) |

### Ключевой вывод для диплома

NLP-pipeline после fine-tune может достичь **сопоставимого качества** с LLM при **100x меньшей latency** и **5x меньшем потреблении ресурсов**. Однако LLM лучше обобщает на unseen типы жалоб благодаря масштабу предобучения.
